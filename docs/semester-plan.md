## 怎样加快进度

1. 每个人有“当前必做”与按顺序列出的“提前完成后继续”。完成当前验收、提交可审阅 PR 后，可以更新原 Issue 并直接做下一项，不等周末或下周；PR 待审时先做不依赖未合并改动的部分。
2. 提交不等于完成。当前项完成需要适用检查和操作证据、合并或明确接入状态；不能跳过真人／目标设备验收。一个已拆小的任务可先交代码，实机证据继续保留未完成。
3. 每人原则上一个主要在做的任务。后续任务涉及同一文件或公共接口时先协调，避免多个分支同时改入口、合同与构建配置。已有依赖就写明，不复制另一人的模块。
4. 工时是安排学习、实现、验证的参考，不是最低耗时、进度上限或必须等满的时间。任务量根据实际成果、依赖与个人可用时间滚动调整，不为凑工时堆报告。
5. 阻塞时当天写清“缺谁的什么输入、已经试了什么、可以继续哪项”。无 API 配置先做接入要求、输入转换和异常映射；无镜子先做 RGB／软件回归。不要因一项条件缺失停止全部工作。
6. 同版本联调至少每周一次；依赖已经齐备就提前联调，10/24–25 是本周协调窗口，不是禁止提前验证的日期。成员实际可用时间在 Issue 协商，不代约。

## 范围和验收纪律

- 优先完成真实 RGB 预览与真实 API 生成闭环，再补已确认核心能力；工期有余继续性能、失败恢复和可解释性，不能只追求功能数量。
- 微调成果不能替代外部 API 主线交付，主线也不负责等待或维护训练流程；负责人保留硬件／视觉和审阅职责，探索时间自行平衡。

- 三品类组合二维预览已有实现；整套模型生成、耳环／腰带、精确量体、真实布料仿真和完整运营后台暂不列核心承诺。
- 模拟服务保留用于开发和故障回归，始终显示 MOCK。提前完成不降低权限、资源清理、素材来源、真实／模拟区分或 PR 审查标准。
