# 负责人拿到硬件后核对什么

目的：确定现有 Android 工程能否直接运行、RGB/深度能否取到，以及下一步要接哪个 SDK。先取得下面的事实，再决定适配方案；“插上有画面”只能证明一种采集通路，不能证明深度已对齐。

2026-10-14 的有效设备信息见 [当前设备记录](hardware-status.md)：负责人报告主机 ZC-3588A、Android 15、8 GB / 128 GB、触摸可用，有线摄像头已找到但接口尚未匹配。此前 S40 型号、供电与不开机记录已撤回；本表是检查方法，不是已经实测完成的参数表。

## 第一次接触时，先拿齐六项资料

1. **主机和摄像头各自的品牌、完整型号、接口照片。** “智能镜”“深度摄像头”不是可查询的型号。确认显示屏是否自带计算主机，摄像头是内置、USB 还是网络连接。
2. **实际操作系统。** Android / Windows / Linux、版本、CPU 架构、内存；大屏可能只是显示器，真正运行程序的是另一台主机。现有 APK 面向 Android 6.0/API 23 及以上，CPU/厂商 SDK 兼容性仍需实测。
3. **开发权限。** 能否安装自己的 APK、打开 USB 调试、用数据线连接电脑；是否存在应用白名单、设备管理限制或只能用厂家签名。记录允许的操作，不自行假定拥有系统管理员权限。
4. **摄像头 SDK 下载地址、版本、说明和能运行的官方示例。** 重点问是否有 Android Java/Kotlin 接口及对应 CPU 的 native 库；只有 Windows 示例或“支持 USB”不能证明 Android 可接入。
5. **RGB 和深度的输出规格。** 是否能同时取流，分辨率/FPS、像素格式、深度单位和无效值，以及官方是否提供 RGB/Depth 对齐与标定参数。
6. **实际安装与网络条件。** 屏幕方向/分辨率/触摸，摄像头高度与可用站位距离，USB 供电与数据线规格，主机能否访问开发后端和后续云端服务。

把官方文档和示例链接留在 Issue，设备报告按下面模板填写。拿不到的信息写“待厂家/老师确认”，不要根据外观猜型号。

## 现场核对表

| 项目 | 要记录的事实 | 为什么影响开发 |
| --- | --- | --- |
| 主机 | 品牌、型号、OS/版本、CPU ABI、RAM/可用存储 | 决定 APK、模型和 SDK 是否兼容，以及图片处理预算 |
| 屏幕 | 像素分辨率、横/竖屏、尺寸、触摸是否可用 | 决定布局、按钮尺寸和显示变换 |
| 摄像头 | 型号、固件版本、连接方式、可见设备列表 | 决定 CameraX 能否使用，或必须写厂商采集适配器 |
| RGB | 同时开深度时的宽高/FPS、RGB/BGR/YUV 等格式、方向/默认镜像 | 决定转换和帧率；内部输出必须竖正且未镜像 |
| Depth | 宽高/FPS、16 位/浮点等格式、毫米/米/比例系数、无效值 | 不能把原始数值直接当毫米；要按实际 SDK 转换 |
| 同步与对齐 | 同步时间戳、硬件同步/软件同步、RGB 对齐深度接口、内外参/畸变参数 | 服装遮挡需要与 RGB 同一坐标、同一时刻的深度 |
| 有效距离 | 官方标称范围、现场能稳定看到完整上半身/全身的距离 | 先确认站位是否可用，再实现“太近/太远”提示 |
| SDK | 支持的 OS/ABI/API level、版本、许可证/分发要求、示例构建方式 | 避免代码能编译但设备缺库或不允许发布 |
| USB/供电 | USB 版本、线材、供电方式、经过 Hub 与否、反复连接是否稳定 | 低帧率、黑屏和掉线可能先是连接问题 |
| 网络 | 开发电脑/主机能否互访，是否有代理/认证页，是否允许访问云端 HTTPS | Android 模拟器地址 10.0.2.2 不能照抄到真实设备 |
| 可维护性 | 重启后能否再开程序、USB 重连、是否需手动授权、可导出日志的位置 | 决定课程演示和现场异常恢复流程 |

CameraX 目前只尝试系统暴露的前/后置 RGB 摄像头。USB 摄像头、厂商深度设备或仅提供外置 SDK 的相机，必须实际核对采集接口，不能把未显示在 App 里直接判为设备损坏。

## Android 主机的只读检查

先在电脑安装 Android Studio 的 SDK Platform-Tools；在设备允许的情况下打开开发者选项和 USB 调试，用数据线连接并接受该电脑的调试授权。以下命令不会安装应用或修改系统设置：

```powershell
adb devices -l
adb shell getprop ro.product.manufacturer
adb shell getprop ro.product.model
adb shell getprop ro.build.version.release
adb shell getprop ro.build.version.sdk
adb shell getprop ro.product.cpu.abilist
adb shell cat /proc/meminfo
adb shell wm size
adb shell wm density
adb shell pm list features
```

多台设备连接时用 `adb -s <设备序列号> ...` 指定设备。如果显示 unauthorized，先处理屏幕上的调试授权；如果电脑完全看不到设备，先核对数据线、驱动与设备是否允许 ADB。不能用 ADB 时，在“设置→关于设备”及厂商资料记录同样的信息。

序列号、账号、Wi-Fi 密码和 SDK 授权码不必发布到仓库。报告保留型号与版本即可。主机为 Windows/Linux 时，不执行上述 Android 命令；记录 OS、CPU/GPU、摄像头官方 Demo 与 SDK 平台后再确定架构。

## 第一次实测的顺序与记录

1. **厂家 Demo：** 先单独看到 RGB、深度，再同时看到两路，记录实际宽高/FPS和错误；确认是否存在对齐后的深度输出。
2. **项目诊断页：** 在 Android 主机安装调试 APK，先跑合成样例，再点 RGB 并授权。记录是否能取到帧、实际画幅、人体跟踪状态和“处理输出 FPS”。这个 FPS 不等于相机采样 FPS。
3. **人物与方向：** 正面站立、左右移动、远近移动、抬手、转身、出框和重新进入；检查左右、镜面和旋转。记录站位距离、照明、失败步骤，不只写“正常”。
4. **恢复：** 拒绝后重新授权、切到后台再返回、停止后重开、摄像头拔插与重连（外接设备适用）。每次检查旧图是否消失、是否重复占用相机。
5. **短时稳定性：** 首次连续运行 10–15 分钟，记录开始/中间/结束的输出帧率、内存、是否明显发热和掉线。后续再安排长时间压力验证；短测通过不能代表全天稳定。

深度适配尚未完成时，只记录厂家 Demo 能力和待接入内容。不要把合成人体样例当成设备人体识别精度，也不要把缺失 depth 的输出写成遮挡验证通过。
